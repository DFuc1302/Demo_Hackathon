# Gap analysis — M0

## Decision and evidence boundary

Keep the working `backend/app` + `frontend` architecture. Add a backend/CLI-only configurable pipeline in M1 after review; do not move the repository into the candidate top-level `src/` layout. This audit implements nothing beyond the three M0 documents (`OMP_RMIT_Hackathon_Development_Plan.md:9–29`). `docs/CURRENT_ARCHITECTURE.md` contains runtime evidence and the complete pre-existing dirty-tree summary; `docs/MIGRATION_PLAN.md` defines future review gates.

Classifications describe disposition, not changes made during M0. KEEP preserves contracts; REFACTOR is a later bounded extension; REPLACE/REMOVE authorize no action now; NEW identifies missing capability. Every component group below has a disposition.

## Observed risks (not hypothetical challenge requirements)

| Risk | Evidence | Consequence / later acceptance constraint |
|---|---|---|
| Artifact size/startup cost | Local English/XLM-R/M2M100 weights are approximately 0.568/1.112/1.936 GB; `backend/app/main.py` eagerly loads English and attempts optional multilingual at startup. | Disk/model loading and CUDA memory are material. No latency/VRAM benchmark was performed; benchmark before deployment claims. |
| Optional initialization hides reasons | `backend/app/main.py` catches all multilingual startup exceptions; local schema-3 validator rejects Hausa translation recall; model-info reports only availability. | Fail-closed English-independent behavior is good; missing versus rejected artifacts look identical. Add reporting later without weakening gates. |
| Queue/event-loop pressure | `backend/app/main.py` has unbounded asyncio queue and synchronous batch inference; eight-prompt/50 ms batch limits are not queue capacity. | No global bounded backlog guarantee. Record as reliability risk; no M0 throttling/refactor. |
| In-memory rate limiting | `backend/app/rate_limiter.py` stores buckets per process, without eviction; only analyze routes are limited. | Multi-worker limits differ; completion/red-team are outside this limiter. Do not claim production-wide DoS protection. |
| Origin/deployment coupling | `backend/app/main.py` fixed local 5173/8080 origins plus FRONTEND_URL; `frontend/src/api.js` build-time loopback default; nginx has no API proxy. | Nonlocal deployments require coordinated endpoint/origin config and browser verification. |
| Local/ignored data and external access | `.gitignore`, manifests, preparation scripts and `backend/Dockerfile` copying local models. | Clone-to-run depends on artifact preparation and model/data/package access. A docs-only commit cannot publish the pre-existing untracked implementation. |
| Windows/WSL differences | Current WSL npm resolves under Windows Program Files; `README.md` documents PowerShell; CI uses Linux Node 24 while frontend Docker uses Node 20. | Use Windows build on this workstation; do not mutate/reinstall platform-specific dependencies indiscriminately. Docker compatibility remains unverified. |
| Red-team demo setup discrepancy | Five cases in `backend/app/redteam.py`; local endpoints need ALLOW_LOCAL_REDTEAM; compose declares no fake target service. | Older three-case/turnkey demo claims are inaccurate; document explicit setup, do not silently permit private targets. |
| Dirty-tree commit contamination | Baseline 0 staged/22 modified/38 untracked files; `git log` still at Windows-setup-era commits. | Stage only the three M0 files. Later milestones must isolate intentional files; never sweep V2/multilingual work into an unrelated commit. |

## Assumptions / unverified

The official theme is only handoff evidence, not verified rules. Challenge labels/task type/languages/metric/splits, raw data availability/licensing, sample-submission format, authorized transformations, external credentials/network/cost policy and ensemble permission are unresolved. No API keys, `.env` contents, private datasets or credential settings were inspected. M2/M5 depend on actual task need; native-speaker quality is not established by translated pilot metrics. Tests/build/API results apply only to the current working tree and are recorded in `docs/CURRENT_ARCHITECTURE.md`; they do not establish fresh-clone, Docker or challenge readiness.
